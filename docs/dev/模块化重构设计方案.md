# Naiba Chat 模块化重构设计方案

> v0.1 草案（待评审）。范围：**仅后端**；目标：**`naiba/` 包 + 领域分层 + 单向依赖 + `server.py` 门面**；前置约定：**阶段 0 顺带修复既有缺陷与死代码、补测试护栏**。
>
> 本方案基于 5 份只读深读报告（server 上帝模块 / 模型·视觉·搜索层 / Skill·MCP 层 / 任务·Job·计划层 / 存储·工具·前端），所有行号均为 2026-09 提交 `e8bb87b` 下实测行号。

## 0. 背景与目标

### 0.1 现状

- 后端 20 个 Python 文件平铺根目录，约 2.4 万行；前端 `public/app.js` 单文件 7855 行（**本轮不动**）。
- `server.py`（5575 行）同时承担：HTTP 传输层（约 1000–1200 行）、`NaibaChatApp` 组装根、`ConfigStore` 配置 CRUD（约 1120 行）、大量与 HTTP 无关的纯函数工具。
- 各 runtime 文件"名义上已拆分"，但通过 **9 处函数级延迟 `from server import ...`** 反向借用纯函数，构成逻辑环；`APP` 全局被引用约 197 处（统计口径 ±3），使模块间实际咬合。
- `tests/` 仅 2 个有效测试文件（`test_updater.py`、`test_workspace_binding.py`），**无任何 server.py 路由测试**；`tests/__pycache__` 磁盘上残留 **15 个 pyc**（12 个不同测试模块名：test_regressions / test_runs / test_plan6 / test_plans / test_plan4 / test_permission_modes / test_comfyui_tools / test_capability_runtime / test_model_profiles / test_diagnostics / test_harness_primitives / test_build36，其中 plan4 / plan6 / regressions / runs 存在 3.12 与 3.14 双版本），说明这些测试曾在本机跑过；但 `git ls-tree 30e860e~1:tests` 只有现役 2 个文件、git 历史中亦无删除记录（唯一相关删除是 1.4.2 的旧测试）——**源码从未入库，无法从 git 恢复**，只能按行为规格重建（§5.2）。

### 0.2 目标

1. 后端逻辑迁入 `naiba/` 包，按领域分层，**依赖方向单向（DAG）**：
   - 低层禁止 import 高层；运行时**永不 import server 包**；跨层共享一律走注入（构造参数 / 回调 / 窄 Protocol）。
2. `server.py` 退化为**门面 shim**（re-export + `main()` 委托），保证 `launcher.py`、`tests/test_workspace_binding.py`、PyInstaller spec（入口 `launcher.py`）与既有调用点**零改动**。
3. 对外 HTTP API 路径、事件流协议**版式不动**，只挪代码归属；前端不需要任何配合。
4. 按阶段推进：每阶段独立提交、独立验证、可回滚；阶段 0 修复缺陷 + 清死代码 + 补护栏。

### 0.3 不变量（任何阶段都不得破坏）

- 端点路径与 HTTP 语义不变；事件 `type` 与负载字段不变；SSE/NDJSON 流式协议不变。
- `run_events` 表 PK(run_id, sequence) 与 sequence 分配语义不变。
- Run/Job 取消竞态防线不变：`_run_chat` 取消双检（L844/L850/L1158/L1226-1229）、`_persist_aborted_message` 幂等检查（L1531-1537）、3 秒强制取消看门狗（L1437-1468）。
- 工具确认协议 `NEED_CONFIRM:<id>:<reason>:<args>` 与权限模式（confirm/auto/full/deny）行为不变。
- Skill 注入机制不变：冻结集按字节稳定渲染进 system 尾部（保 DeepSeek 前缀缓存）；/ref 引用以用户消息追加且仅首次；>60000 字符只发 `skill_warning` 事件不截断。
- DeepSeek `reasoning_content` 透传、多模态图片路由、缓存命中率优化逻辑不变。

### 1.3 跨模块隐性契约（阶段 4 类型化对象）

1. **`run_context` 字典**（16 键）：`run_id / job_id / conversation_id / owner_session_id / parent_job_id / depth / allowed_tools / skill_policy / job_registry / executor / cancel_event / vision_budget / interaction_mode / routing_message / pull_interjections / mark_interjections_consumed`；跨 async_tasks / plan_runtime / subagent / tool_registry / skill_runtime / vision_runtime 6 方，无类型定义。
2. **事件 type**（约 25 种）：`delta / reasoning_start / reasoning_delta / reasoning_end / status / skills / tool_start / tool_confirm / tool_result / tool_error / vision_* / debug_cache / error / …`；前端 `handleChatEvent`（app.js L5666-5997）与 async_tasks 负载逐字对齐。
3. **消息 metadata 键**：`attachments / reasoning / tool_runs / trace / usage / files / plan_id / plan_step / plan_step_title / aborted / partial / error`；写入方 async_tasks（L1202-1224 / L1544-1556 / L1644-1656），重放方 `build_model_history`（server L2570-2636）。
4. **storage 表契约**：`background_tasks` 同时承载 run 与 job 两类行（`parent_job_id / owner_session_id / progress / current_step / attempt / checkpoint / result` 为迁移列）；`run_events` PK(run_id, sequence)，`append_run_event` 用 MAX+1 分配，读取默认封顶 500 需分页；`plans.steps` 为 JSON 数组（id/title/detail/status/summary）；`cleaned_jobs` 用于区分"已清理"与"从未存在"。
5. **tools 三层**：内置工具（tool_registry **声明** 39 个 + 系统处理器注册表）→ 实际执行器 `ToolExecutor` **在 skill_runtime L382-1103** → MCP（`mcp__<server>__<tool>` 动态注册，仅重开会话进入可用集）。

## 2. 目标架构（naiba/ 包）

### 2.1 分层与依赖红线

```
层级 4  组装/HTTP   app.py(组装根)  http.py(路由/授权/流式)  launcher.py(不动)
层级 3  编排        run/*  jobs  plans  subagent  skills/agent  capability  search  updater
层级 2  服务        llm/client  vision/{router,client,tools}  skills/{catalog,install,tools}
                    storage  config  mcp  tools/registry
层级 1  纯函数      core/*  llm/{protocols,stream}  vision/images  skills/{policy,protocol,context}
层级 0  零依赖      net  paths(PathContext)  diagnostics  storage/schema
```

红线：低层禁 import 高层；**运行时永不 import `server`**；`server.py` 只被 `launcher.py` 与测试（`from server import` 兼容）引用；`naiba/app.py` 是唯一允许 import 全部子模块的"组装根"。

**补充（2026-09-05 外审修订）**：`server.py` 门面的 re-export **只服务 `launcher.py` 与 `tests/`**（收窄清单见 §4.1）；任何 runtime 不得经 `server` 中转访问 `naiba.*`——阶段 1 起 9 处导入必须**直指 `naiba.core.*`**，不留"先 re-export、以后再改"的过渡态。
